# AGENTS.md

Рабочие правила для ИИ-агентов, работающих с репозиторием **SkyW**.
Репозиторий общий, над ним работает команда: чужую работу не откатывать,
не переписывать и не коммитить вместо автора.

Язык кода, комментариев, документации и этого файла — русский.
Эмодзи не используются: акценты делаются разметкой Markdown.

---

## 1. Три главных правила

### 1.1 Комментарии по делу, не длиннее двух строк

Комментарий объясняет **почему**, а не пересказывает **что** делает код.
Комментарий из двух строк — предел. Если решение требует длинного объяснения,
оно не комментируется в коде, а пишется в `docs/` и ссылается на раздел.

**XML-документации в коде нет.** Не пишутся `<summary>`, `<remarks>`, `<param>`,
`<returns>`, `<exception>`: они пересказывают сигнатуру, повторяются при правке
кода и устаревают раньше него. Всё, что не помещается в две строки, живёт в
`docs/` и в отчёте `log/`.

```csharp
// Хорошо:
// Порог проверяется до сборки текста: не платим за строку, которая отбросится.
if (!_log.IsEnabled(level))
{
    return;
}

// Хорошо, объявление типа:
// Файл переживает перезапуск: пишется без буфера, иначе последние записи терялись бы.
public sealed class FileLogSink : ILogSink
```

```csharp
// Плохо: пересказ кода и комментарии ради комментариев.
// Записываем сообщение в журнал
// Если уровень не включён, то сообщение не записывается
// и возвращаемся из метода, ничего не делая
```

```csharp
// Плохо: XML-документация вместо короткого объяснения.
/// <summary>
/// Записывает сообщение заданного уровня.
/// </summary>
/// <remarks>
/// Освобождение в проверке не учитывается: проверка отвечает за уровень, а не за
/// срок жизни.
/// </remarks>
```

Правила оформления:

- Комментарий оправдан, если без него код понят неправильно. Член с очевидным
  именем не комментируется вовсе.
- Несколько утверждений не склеиваются в один многострочный блок: два коротких
  комментария в разных местах лучше одного на четыре строки.
- Ссылка на требование вместо переска требования:
  `(docs/stack-constraints.md раздел 2)`.
- Удаляй комментарий, который перестал соответствовать коду.

### 1.2 Доводить начатую задачу до идеала

Одна задача — один законченный результат. Нельзя переходить к следующей
задаче, пока текущая не доведена.

Задача считается доведённой, только когда выполнены все пункты:

1. **Собрано.** `dotnet build SkyW.slnx -c Release` без ошибок и предупреждений
   (`TreatWarningsAsErrors=true`).
2. **Доказано.** Тест или воспроизводимый замер подтверждает поведение.
   Утверждение «работает» без проверки не является результатом.
3. **Оптимизировано.** Производительность не хуже: для изменённого горячего
   пути есть замер до и после. Если задача не про производительность —
   это оговаривается явно в отчёте.
4. **Проверено целиком.** `dotnet test --solution SkyW.slnx` — `failed: 0`.
   Код возврата 8 означает «в каком-то проекте тестов ещё нет», а не сбой:
   сейчас его дают пустые `SkyW.Tests.Stack` и `SkyW.Tests.Architecture`.
5. **Записано.** Отчёт и заметки лежат в `log/` (раздел 5).

Запрещено:

- Оставлять задачу наполовину «потом доделаю».
- Переключаться на соседнюю подсистему, пока текущая не доказана.
- Чинить чужую сломанную задачу молча: непонятный чужой сбой — это вопрос
  владельцу, а не повод для правки чужого кода.

Если задача упёрлась в нерешённый вопрос из `docs/engine-architecture.md`
раздел 14 или `docs/answers.md` — остановиться и спросить, а не выбрать молча.

### 1.3 Отчёты и заметки — в `log/`

Каждая законченная задача оставляет в `log/` небольшой отчёт и, при
необходимости, заметки по ходу работы. Формат и правила — в `log/README.md`.

## 2. Что это за проект

2.5D/3D игровой движок: Silk.NET (окно, ввод, рендер), Jolt (физика),
Friflo (ECS), Hexa.NET.Math (математика). Целевой фреймворк `net10.0`,
SDK закреплён в `global.json`.

Каталоги следуют за подсистемами, а не за типами.

| Слой | Проекты | Что внутри |
|---|---|---|
| 1. Контракты | `src/SkyW.Abstractions` | интерфейсы движка, внешних зависимостей нет |
| 2. Подсистемы | `src/SkyW.Mathematics`, `src/SkyW.Diagnostics`, `src/SkyW.Content`, `src/SkyW.Scenes` | математика, профилирование и логирование, форматы ресурсов, сцены и префабы |
| 3. Сервисы | `src/SkyW.Simulation`, `src/SkyW.Rendering`, `src/SkyW.Input` | планировщик и снимки, рендер-конвейер, логика ввода |
| 4. Реализации | `src/SkyW.Backends.Silk`, `src/SkyW.Backends.Jolt`, `src/SkyW.Backends.Friflo` | единственное место, где допустимо обращение к внешним библиотекам |
| Приложения | `src/SkyW.Host`, `src/SkyW.Sandbox` | композиция зависимостей и демонстрация |

Прочее: `tools/` — самостоятельные инструменты контента, `tests/` — тесты,
`assets/` — контент, `docs/` — документы, `log/` — отчёты агентов.

## 3. Сборка и проверка

```bash
dotnet build SkyW.slnx -c Release
dotnet test --solution SkyW.slnx
dotnet run --project src/SkyW.Sandbox
```

Полезно знать:

- `TreatWarningsAsErrors=true`: предупреждение — это сбой сборки.
- `Nullable=enable`, `ImplicitUsings=enable`, `LangVersion=latest`.
- `AllowUnsafeBlocks=false`, `PublishTrimmed=false` — нативные `.so` из
  `JoltPhysics.Native` тримить нельзя.
- Раннер тестов — Microsoft.Testing.Platform, объявлен в `global.json`.
- Итог тестов смотри по строке `failed`, а не по коду возврата: код 8 дают
  проекты без тестов (`SkyW.Tests.Stack`, `SkyW.Tests.Architecture`).
- Долгие и «спорные» команды запускай с `timeout` и проверяй код возврата.

Инструменты контента запускаются отдельно:

```bash
dotnet run --project tools/SkyW.Tools.Atlas
dotnet run --project tools/SkyW.Tools.Cook
dotnet run --project tools/SkyW.Tools.Terrain
```

## 4. Архитектурные ограничения

Нарушение любого пункта ломает остальные, поэтому проверяется до написания кода.

1. **Слой 1 содержит только интерфейсы.** Внешних зависимостей в
   `src/SkyW.Abstractions` нет вообще.
2. **Внешние библиотеки — только в `src/SkyW.Backends.*`.** Прикладной код
   обращается к интерфейсам движка, реализации их удовлетворяют. Зависимости
   направлены внутрь.
3. **SOLID как основа решений**, а не как формальность: каждая внешняя
   зависимость и платформенная часть скрыта за своим интерфейсом
   (`docs/engine-architecture.md` раздел 1).
4. **Частоты симуляции и рендера раздельные**, симуляция фиксированным шагом
   по умолчанию.
5. **Сбой подсистемы не роняет кадр**: ошибка изолируется, кадр продолжается.
6. **Юнит-тесты подсистем не тянут рендер-бэкенд и нативную физику**: время,
   ввод и хранилище подменяются тестовыми реализациями.
7. **Физический мир обязан вызвать `Foundation.Init`** внутри своей обёртки,
   а не из точки входа: забытый вызов даёт SIGSEGV без управляемого
   исключения (`docs/stack-constraints.md` раздел 2).
8. Граф ссылок должен проверяться проектом `tests/SkyW.Tests.Architecture`.
   Сейчас в нём нет ни одного теста, поэтому правила слоёв держим вручную —
   это пробел, а не гарантия.

Прочитай перед крупной задачей: `docs/engine-architecture.md`,
`docs/stack-constraints.md`, `docs/graphics-art-direction-lowpoly-pixel-3d.md`.
Ответы владельца проекта — в `docs/answers.md`.

## 5. Журнал `log/`

`log/` — короткие отчёты и заметки агентов. Не переписывается и не удаляется:
это история того, как принимались решения.

Имя файла: `log/YYYY-MM-DD-задача.md`, например
`log/2026-10-13-ring-buffer-log-sink.md`.

Отчёт состоит из пяти коротких блоков:

1. **Задача** — что требовалось, одна-две строки.
2. **Что сделано** — список изменённых файлов и суть решения.
3. **Проверка** — чем доказано: команда, тест, замер «до/после».
4. **Открытые вопросы** — что осталось нерешённым и почему.
5. **Дальше** — что логично сделать следующим шагом.

Правила: без дампов логов и простыней кода, только выводы и числа;
заметки по ходу работы — отдельным файлом `log/YYYY-MM-DD-задача-notes.md`,
короткие, по одной записи на смысловой шаг.

Полный формат и примеры — в `log/README.md`.

## 6. Работа в команде

- Начинаешь работу — сначала `git pull`, чтобы не строить решения на устаревшем коде.
- Работай в своей ветке: `git switch -c <короткое-описание-задачи>`.
- В коммит добавляй только свои файлы, явно перечисляя пути. Не используй
  `git add .` и `git add -A`: в рабочем дереве может быть чужое, незакоммиченное.
- `bin/`, `obj/`, `tmp/` в `.gitignore` — не коммитируй артефакты сборки.
- Не делай `push --force` в общие ветки, не переписывай чужие коммиты.
- Сообщение коммита — короткое, в стиле репозитория, со ссылкой на задачу.
- Не чини чужую незавершённую работу и не переименовывай чужие файлы без
  согласования: сначала вопрос, потом правка.

## 7. Частые ошибки агентов

| Ошибка | Как правильно |
|---|---|
| Пересказ кода в комментарии | Комментировать «почему», не длиннее двух строк |
| XML-документация `<summary>` и `<remarks>` | Не пишется: объяснение живёт в `//` до двух строк, подробность — в `docs/` и `log/` |
| Новый тип без объяснения, зачем он | Одна строка `//` над объявлением либо запись в `log/` |
| Новая подсистема «на будущее» без задачи | Сначала требование, потом код |
| Прямое обращение к Silk.NET или Jolt вне `Backends` | Интерфейс в `Abstractions`, реализация в `Backends` |
| Принято решение по спорному пункту молча | Спросить: `docs/engine-architecture.md` раздел 14 |
| Оставил задачу наполовину | Довести по чеклисту раздела 1.2 или явно отметить статус |
| Коммит собрал чужие изменения | Явно перечислить свои пути в `git add` |
| Отчёт на две страницы | Пять блоков из раздела 5, по паре строк |
| Тест написан, но не запущен | Запустить и привести вывод в отчёте |
| Замер без базы | Для горячего пути: замер до и после |
